## 第三轮：重新实现启动器更新（三通道 / GitHub）

### 设计要点
- 新增 `Modules/ModUpdate.vb`（唯一实现），`ModSecret.vb` 里原来的空壳（UpdateCheckByButton / UpdateRestart / UpdateReplace / IsUpdateWaitingRestart / DownloadLatestPCL）全部删除，调用点无需改动（Module 级符号全局可见）。
- 三通道：正式版（Releases 非 prerelease，按语义版本取最大）、测试版（含 prerelease，按 published_at 取最新）、自动构建版（`/actions/workflows/build.yml/runs?branch=main&status=success` 最近一次成功 run，用 head_sha 与本地 `CommitHash` 比较）。
- 下载：Release 直接取 `.exe` 资产；自动构建版优先取 `nightly` 预发布里名字含短 sha 的资产，兜底 nightly.link（artifact zip，需解压）。
- 缓存写设置项 `CacheUpdateResult`（JObject，按通道分键存时间戳/结果），`IsUpdateCheckDue()` 依据 `ToolUpdateCheck`（0 每次启动 / 1 六小时 / 2 每天 / 3 关闭）。
- 自我替换：下载到 `Paths.Base & "PCL\Update\OpenPCL-new.exe"` → 复制为 `Updater.exe` → 以 `--update <pid> <旧exe> <Updater> <0|1>` 启动 → 退出；`UpdateReplace` 等 pid 退出后重试覆盖，失败写 `UpdateFailed.txt`，下次启动 `UpdateStartupCleanup()` 提示。注意更新器进程的 `Paths.Base` 指向暂存目录，故失败标记必须用 `Path.GetDirectoryName(NewFileName)`。
- UI：设置→其他新增「启动器更新」卡片（通道/频率/检查/打开 Releases + `MyLoading` 进度）；关于页恢复「检查更新」；提示用 MyMsgBox（立即更新 / 暂不更新 / 查看详情），立即更新会跳到设置页由卡片显示进度。

### CI

- 新增 `release.yml`：tag `v*` 或 `[0-9]*` 触发，校验 tag 与 `VersionBaseName` 一致，构建 Release 并用 softprops 发布，tag 含 `-` 视为预发布。
- 版本号 bump 到 2.99.1.1（VersionCode 417/418），避免当前构建被已发布的 2.99.1.0 反超。

### 编译验证新方法（重要）
本机 `dotnet build` 的 WPF 标记编译不生成 `*.g.vb`，导致 BC30506/BC30590 一片。这次改用 **直接调用 Roslyn vbc** 做真实语义编译：
- 响应文件 `C:\Temp\vbc.rsp`；关键点：`-sdkpath` 指向 `Reference Assemblies\...\v4.8`、`-imports:` 必须带上 vbproj 里的 `<Import Include>` 列表（否则 WPF 类型全丢）、补 `Facades/netstandard.dll` 与 `System.IO.Compression(.FileSystem)`。
- bash 调 vbc 必须 `MSYS_NO_PATHCONV=1` 且用 Windows 路径，否则 `/r:` 被 MSYS 当路径改写。
- 结果：`ModUpdate.vb` 与新处理器零错误；仅剩 28 个 `Computer 不明确` 之类环境噪声（未改动文件同样报）。对新控件可临时往 `obj/Debug/**/*.g.vb` 补 `Friend WithEvents` 字段来验证 Handles，验证后必须还原。
- 坑：.NET Framework 4.8 没有 `String.Contains(String, StringComparison)`，要用 `IndexOf(..., StringComparison) >= 0`。

### 遗留
- `nightly` 预发布要等 build.yml 推到 main 跑一次才会出现；自动构建版在那之前只能走 nightly.link 兜底。
- 发布新版本需先改 `VersionBaseName` 再打同名 tag，否则 release.yml 会直接失败。

## 构建修复：禁用 ClickOnce 应用清单签名

- 症状：构建报「在证书存储区中找不到清单签名证书」。
- 原因：`Plain Craft Launcher 2.vbproj` 保留了 VS 生成的 ClickOnce 签名配置
  `SignManifests=true` + `ManifestCertificateThumbprint=CE7A815C…` + `ManifestKeyFile=Plain Craft Launcher 2_TemporaryKey.pfx`，
  而该 pfx 并未入库、证书也不在本机证书存储区。
- 处理：`SignManifests` 改 `false`，删除 `ManifestCertificateThumbprint` / `ManifestKeyFile` 两个 PropertyGroup。
  `GenerateManifests=true`、`ApplicationManifest=app.manifest` 保持不变（app.manifest 仍需嵌入）。
- 验证：`-getProperty` 求值得 SignManifests=false、thumbprint/keyfile 为空；
  MarkupCompile 产出的 `obj/*/Pages/**/*.g.vb` 已正确包含新增控件（BtnUpdateCheck / ComboUpdateChannel / LoadUpdate / BtnAboutUpdate）。
- 备注：dotnet SDK 10 的构建仍报 501 个 BC30506/BC30590，原因是该 SDK 的 Compile 项不含 pass2 生成的 `.g.vb`，
  属工具链问题（基线同样报 523 个），只能用 VS 的构建或 CI 验证。

### 追加：关闭 ClickOnce 清单生成（解决 Common-Controls 报错）

- 症状：禁用签名后紧接着报「未能找到文件 Microsoft.Windows.Common-Controls, Version=6.0.0.0, ...」。
- 原理：`GenerateManifests=true` 时 `GenerateClickOnceManifests` 也为 true，走 `_SetExternalWin32ManifestProperties`
  → `GenerateApplicationManifest` 把 app.manifest 当基础清单，要求每个依赖解析成真实文件并计算哈希；
  comctl32 v6 是系统 Win32 程序集，无对应文件 → 必然失败。
- 处理：`GenerateManifests` 改 `false`。此时走 `_SetEmbeddedWin32ManifestProperties`，
  `Win32Manifest=app.manifest` 直接嵌进 exe，依赖解析与签名都不再发生。
- 求值验证：GenerateClickOnceManifests=false、Win32Manifest=app.manifest、EmbeddedWin32Manifest=app.manifest、NoWin32Manifest 为空。
- 副作用（正向）：不再生成 exe 旁的 `.exe.manifest`；CI 两个工作流只拷 exe，所以内嵌清单更可靠，
  DPI/长路径/comctl32 设置不会因缺少伴生文件而丢失。
- 注：`CoreBuildDependsOn` 里 GenerateManifests 排在 Compile 之后，所以本地 dotnet 构建**看不到**这类清单错误，
  只有编译能过的环境（VS / CI）才会暴露。
